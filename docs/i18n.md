# Following UltraStar's language setting

The plugin follows the language the game is set to, with no further change to UltraStar
Deluxe. This file records both halves: what the game turned out to expose, and what was
built on top of it.

Everything in the first half was verified at runtime with a probe plugin inside the patched
build, not inferred from reading the source. The probe was throwaway; the findings are what
matter.

**Short version.** The active language is plain text in `config.ini`, reachable through
`Usdx.GetUserPath()`. `src/tagger/i18n.lua` carries our own message catalogues keyed by the
same language names the game uses. The interface is translated, including the display names
of tags; the tag written into a song folder is never translated, because that is the part
people grep.

## What the game exposes

### 1. The language name, from `config.ini`

`Usdx.GetUserPath()` returns the directory holding `config.ini`, and the language sits in
plain text at the top of it:

```ini
[Game]
Language=German
```

Verified in the game:

```text
Usdx.GetUserPath() = C:\Users\Valentin\Documents\USDX\game\
config.ini read ok, 2362 bytes
[Game] Language = English
```

The value is the **base name of a language file**, not a locale code. UltraStar writes it as
`ILanguage[Language]` (`src/base/UIni.pas:1869`) and reads it back with a default of
`English` (`src/base/UIni.pas:1547`), where `ILanguage` is populated by enumerating
`<install>/languages/*.ini` (`src/base/ULanguage.pas` `LoadList`). So the vocabulary is
exactly that set of file names — 29 of them in `v2026.8.1`: `Catalan`, `Chinese`,
`Croatian`, `Czech`, `Danish`, `Dutch`, `English`, `Euskara`, `Finnish`, `French`,
`Gaelic`, `Galician`, `German`, `Greek`, `Hungarian`, `Icelandic`, `Italian`, `Japanese`,
`Luxembourgish`, `Norwegian`, `Polish`, `Portuguese`, `Romanian`, `Russian`, `Serbian`,
`Slovak`, `Slovenian`, `Spanish`, `Swedish`.

They are ASCII English identifiers. There is no BCP-47 tag, no region, and no fallback
chain to consult.

**Freshness is not a problem.** The value is written when the user leaves the game options
screen (`TScreenOptionsGame.Leave` → `Ini.Save`, `src/screens/UScreenOptionsGame.pas:264`),
and that is the only place a language change is persisted — there is no save on exit, only
a first-run save during startup and one on the Alt+Enter fullscreen toggle. Since the
options screen has to be left before song selection can be reached again, re-reading
`config.ini` lazily always sees the current value; there is no in-memory-versus-disk skew a
player could observe. Re-reading on each `ScreenSong.SongSelected` is more than enough.

### 2. The game's own translations, via `current_filename`

`languages/` lives under the *shared* install path (`src/base/UPathUtils.pas:192`), which
the Lua API does not expose — `GetUserPath()` is a different directory on any non-portable
install. But `ULuaCore` sets a global to the plugin's own absolute path immediately before
calling `plugin_init` (`src/lua/ULuaCore.pas:721-723`):

```lua
current_filename  -- C:\...\game\plugins\usdx-tagger.usdx
```

Walking up from there and probing for `languages/English.ini` locates the install tree.
Verified, along with reading real translations out of it:

```text
current_filename = C:\Users\Valentin\Documents\USDX\game\plugins\i18nprobe.usdx
languages dir    = C:\Users\Valentin\Documents\USDX\game\languages
  LANGUAGE           = English
  SONG_MENU_PLAY     = Sing
  SCREENSHOT_SAVED   = Screenshot saved
  MSG_ERROR_TITLE    = Error
```

The format is the same trivial INI as `config.ini`: a `[Text]` section, `KEY=Value`, UTF-8,
`;` for comments. The `LANGUAGE` key holds the language's own name for itself
(`German.ini` → `Deutsch (German)`), which is what the options screen displays.

### 3. Non-ASCII text renders correctly

`Usdx.Text.Print` and `Usdx.Text.Width` take a `UTF8String`
(`src/base/UText.pas:75-76`), and `src/base/UMain.pas:115` calls
`SetMultiByteConversionCodePage(CP_UTF8)`, so the `String` → `UTF8String` assignment inside
`ULuaText_Print` is a no-op and the bytes handed over from Lua arrive intact. Fonts are
FreeType with UCS-4 glyph loading and Noto fallbacks (`game/fonts/fonts.ini`).

Measured through `Usdx.Text.Width` at size 30:

| text | code point | width |
|------|-----------|-------|
| `a`  | U+0061 | 12.36 |
| `aa` | —      | 24.72 |
| `ä`  | U+00E4 | 12.36 |
| `ж`  | U+0436 | 16.52 |
| `α`  | U+03B1 | 13.72 |
| `歌` | U+6B4C | 22.03 |

`ä` measures exactly one `a`, not two — its two UTF-8 bytes became one glyph rather than two
mojibake characters. Cyrillic, Greek and CJK each measure as a single glyph at a
script-appropriate width, so the fallback chain resolves them too. Translated strings can be
displayed as they are.

## How it works

`src/tagger/i18n.lua` holds the catalogues; `adapter.lua` reads the game's setting;
`init.lua` routes every user-visible string through `i18n.t()`.

### Our own catalogues, not the game's

Reusing UltraStar's translations is tempting and mostly a trap. It has no key for *tag*,
*tags*, *tag added* or *tag removed* — the plugin's entire vocabulary is absent, so almost
every string would have to be contributed upstream to 29 files and then shipped by whatever
build the user happens to run. And those files are themselves patchy:

| | keys |
|---|---|
| English (the source) | 739 |
| German | 650 |
| Slovenian | 613 |
| French | 509 |
| Russian | 342 |
| Serbian | 278 |

UltraStar hides the gaps by falling back to its English entries (`TLanguage.Create` builds
`EntryDefault` from `English.ini`). A plugin reading the `.ini` directly gets no such help —
a missing key is simply `nil`, and the fallback would have to be implemented on our side
anyway. Our own catalogue is less code and fully under test.

### Named placeholders, not positional ones

Lua's `string.format` has no `%1$s`, so a language needing the song before the tag would be
stuck with English word order. Catalogue entries use named holes instead:

```lua
tag_added = 'Added tag "{tag}" to {song}'   -- English
tag_added = 'Tag "{tag}" zu {song} hinzugefügt'  -- German
```

A translation can reorder them, or leave one out entirely. A hole with no value is rendered
as `{name}` rather than erased, so a mistake is visible instead of silent, and never an
error at a keypress.

### Two renderings of every message

`i18n.t()` gives the user's language. `i18n.en()` always gives English, and the log uses it,
because log lines end up in bug reports read by people who do not share the player's
language. So a German player tagging a song sees

```text
Tag "schlecht" zu Björk - It's Oh So Quiet hinzugefügt
```

while `Error.log` records

```text
INFO: usdx-tagger: Added tag "bad" to Björk - It's Oh So Quiet
```

### Tag names: translated on screen, canonical on disk

Tag *display* names are translated. The tag *written to the file* never is.

That distinction is the whole point. The tags are payload, not interface: they get grepped
([README](../README.md#working-with-tags-outside-the-game)) and song folders travel between
machines and between people. If a German UI wrote `schlecht`, `grep -- "- bad"` on someone
else's library would silently miss those songs, and one library tagged on two machines would
end up with two names for one concept. So `bad` is `bad` in every language, as are the
file's own keys (`version`, `tags`).

The menu therefore shows both:

```text
Tags  (auf/ab, Enter schaltet um, Esc schließt)
> [x] schlecht (bad)
  [ ] prüfen (review)
  [ ] Ton fehlerhaft (bad-audio)
```

The parenthesis is deliberate. A player who only ever sees `schlecht` has no way of knowing
to search for `bad` afterwards, which would defeat the reason the file exists. Notifications
show the translated name alone; the menu is where the vocabulary is learned. English has no
label table at all — its display name *is* the canonical name, so the English interface is a
direct mirror of the file.

### Choosing the language

`i18n.resolve(setting, game_language)` decides, in this order:

| Setting | Result |
|---|---|
| a language we have a catalogue for | that one — `pinned` |
| `auto` (the default) and the game reports one we have | that one — `following` |
| anything else | English — `default` |

`language=` in `usdx-tagger.ini` accepts `auto` or a language name, so a player can keep the
plugin in English while playing the game in German. A name with no catalogue is warned about
in the log rather than accepted silently, because pinning to a language that then shows
English looks like the setting was ignored.

The setting is re-read on song selection, at most every three seconds, so switching
UltraStar's language takes effect without restarting the game. That interval exists to avoid
reading a file on every step of a roulette spin, not to catch a fast-moving value: the game
only persists a language change when the options screen is left.

### What the tests check

Beyond the usual behaviour, the suite treats the catalogues as data to be validated, since
that is where a translation contribution goes wrong:

- every translated string uses exactly the placeholders English uses — no typos, none
  dropped, none invented
- no translation carries a key English does not have
- no entry is empty or still says TODO
- every label table covers every suggested tag, so no menu is half-translated
- label keys are canonical tag names, i.e. they survive `tagset.normalize`
- every string is valid UTF-8, because it goes straight to `Usdx.Text.Print`
- the log rendering contains the canonical tag name and no translation

Those checks were confirmed to actually fail: seven deliberate mutations — a placeholder
typo, a dropped placeholder, an invented key, an empty string, a leftover TODO, a broken
UTF-8 byte, and a German entry left in English — were each caught by the suite.

The built plugin is then driven through the real path with the game stubbed out: a
`config.ini` written to the stub user path, the language re-read mid-session, the German
strings asserted on screen, English asserted in the log, and `- bad` asserted in the file.

### Translation status

English is the source and is complete by construction. German, French, Spanish, Italian,
Dutch, Portuguese, Polish, Russian and Swedish are written but **have not been reviewed by a
native speaker** — they are a starting point, not a guarantee. Corrections are a data-only
change to one table.

The remaining 20 languages UltraStar ships fall back to English. Adding one is also
data-only: a `CATALOGUES.<Name>` table and, optionally, a `TAG_LABELS.<Name>` one. The
renderer needs nothing — Cyrillic, Greek and CJK were all measured rendering as single
glyphs through the Noto fallbacks.

This is UI-language following, not full localisation. There are no dates or numbers to
format, no pluralisation beyond what a per-language table can express, and the tag file
stays byte-identical whatever language the game is in.

## Limitations worth recording

**A non-ASCII user path used to break the config read on Windows. Fixed upstream.**
`Usdx.GetUserPath()` originally pushed UTF-8 only, while Lua's `io` reaches the filesystem
through the narrow C runtime and wants the active code page. For an ASCII path the two agree;
under a profile like `C:\Users\Jörg\AppData\Roaming\ultrastardx` they do not, so the
derived `config.ini` path would not open and the plugin saw no language setting.

It now returns **two** values — the path in the encoding `io` expects, via `Lua_PushIOPath`,
then the same path as UTF-8 for display. `adapter.user_path()` returns both, and the plugin
keeps them apart deliberately: the first opens files, the second goes into log lines, which
would otherwise carry mojibake. A build predating the second value gets the first one twice,
which is correct there.

`adapter.game_config_text()` still retries `%APPDATA%\ultrastardx\config.ini` if the
reported path does not open, which covers exactly that older build. `os.getenv('APPDATA')`
comes from the same narrow runtime `io` uses, so it is already in the right encoding — though
that reasoning is from how the narrow CRT works, **not** measured, since this machine's
profile name is ASCII and both encodings coincide.

`current_filename`, which `ULuaCore` pushes raw as UTF-8, has the same problem and no fix.
The plugin does not depend on it; it was only ever a route to the game's own `languages/`
directory, which we decided against reusing.

**Two command-line switches are invisible to Lua.** `-configfile <path>`
(`src/base/UCommandLine.pas:275`) moves the config elsewhere, and `-language <name>`
(`src/base/UCommandLine.pas:244`) overrides the setting for one run without writing it to
disk. Neither is reachable from a plugin, and neither is common. An unreadable `config.ini`
is treated as "language unknown", which falls back to English.

**No pluralisation machinery.** Fine for a fixed set of short strings; a per-language table
can carry whatever forms a given language needs.

**ASCII-only case folding stays as it is.** Tag comparison lowercases ASCII only, which is
already documented, and translating the interface does not change it — tag names are not
translated.

**Only partly exercised in the game.** The plugin loads in the real game against the
two-value `GetUserPath` and reports the language it resolved:

```text
INFO: usdx-tagger: language English, following UltraStar
```

which is the config.ini read working end to end. The translated strings themselves have so
far only been asserted against the built plugin with UltraStar stubbed out; the renderer's
UTF-8 handling was measured separately in the real game (see above), but a full live session
in a non-English language has not been recorded here.
