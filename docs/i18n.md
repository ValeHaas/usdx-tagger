# Can the plugin follow UltraStar's language setting?

**Yes, and without any further change to UltraStar Deluxe.** The game's language is
readable, the game's own translation files are readable, and translated text renders
correctly. Nothing here needs a new Pascal-side API.

Everything below was verified at runtime with a probe plugin inside the patched build, not
inferred from reading the source. The probe is throwaway and is not part of the plugin; the
findings are what matter.

The starting point is the screenshot in [the README](../README.md): the game is in German
and the plugin is in English, in the same frame.

## What the game exposes

### 1. The language name, from `config.ini`

`Usdx.GetUserPath()` returns the directory holding `config.ini`, and the language sits in
plain text at the top of it:

```ini
[Game]
Language=German
```

Verified in the game:

```text
Usdx.GetUserPath() = C:\Users\Valentin\Documents\USDX\game\
config.ini read ok, 2362 bytes
[Game] Language = English
```

The value is the **base name of a language file**, not a locale code. UltraStar writes it as
`ILanguage[Language]` (`src/base/UIni.pas:1869`) and reads it back with a default of
`English` (`src/base/UIni.pas:1547`), where `ILanguage` is populated by enumerating
`<install>/languages/*.ini` (`src/base/ULanguage.pas` `LoadList`). So the vocabulary is
exactly that set of file names — 29 of them in `v2026.8.1`: `Catalan`, `Chinese`,
`Croatian`, `Czech`, `Danish`, `Dutch`, `English`, `Euskara`, `Finnish`, `French`,
`Gaelic`, `Galician`, `German`, `Greek`, `Hungarian`, `Icelandic`, `Italian`, `Japanese`,
`Luxembourgish`, `Norwegian`, `Polish`, `Portuguese`, `Romanian`, `Russian`, `Serbian`,
`Slovak`, `Slovenian`, `Spanish`, `Swedish`.

They are ASCII English identifiers. There is no BCP-47 tag, no region, and no fallback
chain to consult.

**Freshness is not a problem.** The value is written when the user leaves the game options
screen (`TScreenOptionsGame.Leave` → `Ini.Save`, `src/screens/UScreenOptionsGame.pas:264`),
and that is the only place a language change is persisted — there is no save on exit, only
a first-run save during startup and one on the Alt+Enter fullscreen toggle. Since the
options screen has to be left before song selection can be reached again, re-reading
`config.ini` lazily always sees the current value; there is no in-memory-versus-disk skew a
player could observe. Re-reading on each `ScreenSong.SongSelected` is more than enough.

### 2. The game's own translations, via `current_filename`

`languages/` lives under the *shared* install path (`src/base/UPathUtils.pas:192`), which
the Lua API does not expose — `GetUserPath()` is a different directory on any non-portable
install. But `ULuaCore` sets a global to the plugin's own absolute path immediately before
calling `plugin_init` (`src/lua/ULuaCore.pas:721-723`):

```lua
current_filename  -- C:\...\game\plugins\usdx-tagger.usdx
```

Walking up from there and probing for `languages/English.ini` locates the install tree.
Verified, along with reading real translations out of it:

```text
current_filename = C:\Users\Valentin\Documents\USDX\game\plugins\i18nprobe.usdx
languages dir    = C:\Users\Valentin\Documents\USDX\game\languages
  LANGUAGE           = English
  SONG_MENU_PLAY     = Sing
  SCREENSHOT_SAVED   = Screenshot saved
  MSG_ERROR_TITLE    = Error
```

The format is the same trivial INI as `config.ini`: a `[Text]` section, `KEY=Value`, UTF-8,
`;` for comments. The `LANGUAGE` key holds the language's own name for itself
(`German.ini` → `Deutsch (German)`), which is what the options screen displays.

### 3. Non-ASCII text renders correctly

`Usdx.Text.Print` and `Usdx.Text.Width` take a `UTF8String`
(`src/base/UText.pas:75-76`), and `src/base/UMain.pas:115` calls
`SetMultiByteConversionCodePage(CP_UTF8)`, so the `String` → `UTF8String` assignment inside
`ULuaText_Print` is a no-op and the bytes handed over from Lua arrive intact. Fonts are
FreeType with UCS-4 glyph loading and Noto fallbacks (`game/fonts/fonts.ini`).

Measured through `Usdx.Text.Width` at size 30:

| text | code point | width |
|------|-----------|-------|
| `a`  | U+0061 | 12.36 |
| `aa` | —      | 24.72 |
| `ä`  | U+00E4 | 12.36 |
| `ж`  | U+0436 | 16.52 |
| `α`  | U+03B1 | 13.72 |
| `歌` | U+6B4C | 22.03 |

`ä` measures exactly one `a`, not two — its two UTF-8 bytes became one glyph rather than two
mojibake characters. Cyrillic, Greek and CJK each measure as a single glyph at a
script-appropriate width, so the fallback chain resolves them too. Translated strings can be
displayed as they are.

## Recommendation

Follow the game's language, but **ship our own catalogue** rather than reusing UltraStar's.

Reusing the game's translations is tempting and mostly a trap. UltraStar has no key for
*tag*, *tags*, *tag added* or *tag removed* — the plugin's entire vocabulary is absent, so
almost every string would have to be contributed upstream to 29 files and then shipped by
whatever build the user happens to run. And those files are themselves patchy:

| | keys |
|---|---|
| English (the source) | 739 |
| German | 650 |
| Slovenian | 613 |
| French | 509 |
| Russian | 342 |
| Serbian | 278 |

UltraStar hides the gaps by falling back to its English entries
(`TLanguage.Create` builds `EntryDefault` from `English.ini`). A plugin reading the `.ini`
directly gets no such help — a missing key is simply `nil`, and the fallback has to be
implemented on our side anyway. At that point our own catalogue is less code and fully
under test.

Sketch:

- `src/tagger/i18n.lua` — catalogues keyed by UltraStar language name, `t(key, ...)` with
  `string.format` substitution and a per-key fallback to English. English is complete by
  construction because it is the source text.
- `adapter.lua` gains `game_language()`: reads `[Game] Language` from
  `<GetUserPath()>config.ini` and caches it. This keeps the rule that `adapter.lua` is the
  only module that knows the game exists.
- A `language` setting, default `auto`, accepting any UltraStar language name so a player
  can pin the plugin to English while playing the game in German.
- A language with no catalogue falls back to English wholesale, which reads better than a
  half-translated menu.

Reuse from the game is worth it for exactly the handful of words that already exist and
already mean the same thing — `MSG_ERROR_TITLE`, `OPTION_VALUE_ON`, `OPTION_VALUE_OFF` —
and only as a nicety.

### Tag values must never be translated

The tags are the file's payload, not UI. They get grepped
([README](../README.md#working-with-tags-outside-the-game)), and song folders travel between
machines and between people. If a German UI wrote `schlecht`, then
`grep -- "- bad"` on someone else's library would silently miss those songs, and the same
library tagged on two machines would end up with two names for one concept.

So: translate the menu header, the labels around the tags, the notifications and the error
messages. Never the tag names, and never the file's keys (`version`, `tags`).

This is UI-language following, not full localisation. There are no dates or numbers to
format, and the tag file stays byte-identical whatever language the game is in.

## Limitations worth recording

**A non-ASCII user path breaks the config read on Windows.** `Usdx.GetUserPath()` pushes
UTF-8 (`src/lua/ULuaUsdx.pas:166-167`: `ToUTF8(true)` then `lua_pushstring`) rather than
going through `Lua_PushIOPath`, which is what converts to the active ANSI code page for the
song paths. Lua's `io` reaches the filesystem through the narrow C runtime, so on a
non-portable install under a profile like `C:\Users\Jörg\AppData\Roaming\ultrastardx` the
derived `config.ini` path will not open, and the plugin sees no language setting. The same
applies to `current_filename`, which `ULuaCore` pushes raw.

This affects the plugin's own settings file today, for the same reason, and is worth fixing
on the UltraStar branch by routing `GetUserPath` through `Lua_PushIOPath` — out of scope
here.

A pure-Lua mitigation exists: `os.getenv('APPDATA')` comes from the narrow CRT and is
therefore already in the code page `io.open` expects, so a failed open can be retried
against `os.getenv('APPDATA')\ultrastardx\config.ini`. The variable is present and correct
(`APPDATA = C:\Users\Valentin\AppData\Roaming`, verified), but the encoding claim is
reasoned from how the narrow CRT works, **not** measured — this machine's profile name is
ASCII, so both encodings coincide and the test proves nothing. It needs a non-ASCII profile
to confirm.

**Two command-line switches are invisible to Lua.** `-configfile <path>`
(`src/base/UCommandLine.pas:275`) moves the config elsewhere, and `-language <name>`
(`src/base/UCommandLine.pas:244`) overrides the setting for one run without writing it to
disk. Neither is reachable from a plugin, and neither is common. Treat an unreadable
`config.ini` as "language unknown" and fall back to English.

**No pluralisation machinery.** Fine for a fixed set of short strings; a per-language
catalogue can carry whatever forms a given language needs.

**ASCII-only case folding stays as it is.** Tag comparison lowercases ASCII only, which is
already documented, and translating the UI does not change it — tags are not translated.
